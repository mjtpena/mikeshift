# Architecture

How MikeShift is put together: the projects, the threads, how the wheel works, how conversions are written, how the package is built, and how the Explorer right-click entry works. For how it is tested see [testing.md](testing.md); for how a release is made see [releasing.md](releasing.md); for what users can expect see [the limitations](../limitations.md). For which parts other tools could reuse, and why they are not split out yet, see [host-design.md](host-design.md).

## 1. Solution layout

```
MikeShift.sln
Directory.Build.props      net10.0-windows10.0.26100.0, min OS 10.0.17763.0, nullable, warnings are errors
Directory.Packages.props   every NuGet version, pinned centrally (PDFsharp stays on 6.2.4: later versions are not MIT)
src/
  MikeShift.Core/          no UI. Everything that converts, classifies, names and decides.
  MikeShift.App/           WinUI 3 tray app, packaged as MSIX (assembly MikeShift.exe)
  MikeShift.Cli/           console exe (MikeShift.Cli.exe; the `mikeshift` command is an execution alias for it), a thin Main around Core's CliRunner
tests/
  MikeShift.Core.Tests/    xUnit; fixtures are generated at test time
  MikeShift.Cli.Tests/     launches the real MikeShift.Cli.exe as a child process
tools/IconGen/            build-time icon generator: renders assets/brand/mikeshift.svg into every MSIX logo, .ico and docs/images/icon-sheet.png (not shipped)
tools/DragHarness/         scripted drags (real mouse/keyboard input + an OLE drag source, or the real File Explorer) against a running MikeShift.exe
tools/ComInterfaceScan.cs  build-time check that trimming keeps every COM interface whole (run by the build, see section 7)

```

The tray icon is monochrome and follows the taskbar theme: `tray-dark-taskbar.ico` (white glyph) or `tray-light-taskbar.ico` (dark glyph), switched live from `UISettings.ColorValuesChanged` (`Tray/TaskbarTheme.cs`, which reads `SystemUsesLightTheme`). Regenerate all icons with `scripts/make-icons.ps1`; the legibility preview sheet is [icon-sheet.png](../images/icon-sheet.png).

**Surfaces other than the wheel:**

* **Window chrome.** `WindowChrome.Apply` wraps a window's content under a WinUI `TitleBar` (icon + title) with `ExtendsContentIntoTitleBar`, so the caption follows light/dark instead of staying a light system caption over dark content. `MIKESHIFT_THEME=light|dark` forces the XAML theme for testing (`Application.RequestedTheme`, never the OS theme).
* **Toast** (`Hud/ToastWindow`). A frameless popup whose *client area* is sized to the measured content (`ResizeClient`), so text is never clipped. WinUI keeps `WS_DLGFRAME`/`WS_EX_WINDOWEDGE` on a borderless presenter window (they cannot be removed; they come back) and Windows draws them as a classic white and grey 3D frame; the window subclass answers `WM_NCCALCSIZE` with "the whole window is client area", leaving only the DWM border (colour set per theme) and rounded corners. It is created a few seconds after start and cloaked (`DWMWA_CLOAK`) until its first frames are composed, so it never flashes black, fades in over 167 ms (layered alpha; none when animations are off) and pauses its timer under the pointer.
* **Failure dialogs** (`Hud/NoticeWindow`). A non-modal, topmost window laid out like a ContentDialog; it is shown without activation unless the user has been idle for 2.5 s, so a keystroke meant for Explorer never reaches a button.
* **Tray flyout** (`Tray/TrayFlyoutHost`). H.NotifyIcon's `ContextMenuMode.SecondWindow` did not open reliably on Windows App SDK 2.x (and forces items to 32 px), so the icon only raises click commands and the app opens a WinUI `MenuFlyout` itself from a tiny fully transparent host window at the pointer (`ShouldConstrainToRootBounds = false`, so WinUI gives it its own acrylic popup window). Left click = Convert files…, right click or a second launch = the menu.
* **Settings cards.** `SettingsCard` is hand-built (`Styles/SettingsStyles.xaml`); the CommunityToolkit settings controls are compiled for Windows App SDK 1.x and were not added.


Native calls use CsWin32 (source-generated P/Invoke). Every `NativeMethods.txt` in a project is picked up, so each folder lists the Win32 functions it needs next to the code that uses them.

## 2. Process and threading model

```
 hook thread (dedicated, high priority, own message loop)
   WH_MOUSE_LL + WH_KEYBOARD_LL  ->  copy struct, TryWrite to bounded Channel<InputEvent>, CallNextHookEx
                                              |
                                              v
 reader task (thread pool, DragCoordinator)  channel -> WheelController.Enqueue (drops moves while no button is down)
                                              |
                                              v
 wheel thread (dedicated STA, "MikeShift wheel")  owns the wheel window, the OLE drop target (OLE calls it through this thread's
   message loop), the Win2D renderer, DragSession, WheelModel and the animation clock. Idles in MsgWaitForMultipleObjectsEx with
   an infinite timeout; wakes for messages, posted work, or a timer it asked for (a 16 ms frame while animating, the session's
   deadlines, a 50 ms button poll while a drag is active, the idle-memory timer).
                                              |  Drop: snapshot paths, return at once
                                              v
 UI thread (STA, WinUI dispatcher)  tray, toast, settings, welcome, editors, dialogs
                                              |
 thread pool  JobRunner -> ActionDef.Run -> converter (WIC / PDF / Media Foundation / Word)  -> toast + chime on the UI thread
```

* **Hook callbacks do nothing else.** A low-level hook callback that takes longer than the `LowLevelHooksTimeout` registry value is silently removed by Windows with no notification, so the callback allocates nothing and takes no locks. `LowLevelInputMonitor` also runs a watchdog: if the left button has been down for a while and no event arrived, it installs fresh hooks before removing the old ones. It sits behind `IInputMonitor` so a Raw Input implementation can replace it.
* **The hotkey thread** (`HotkeyService`, "MikeShift hotkey": STA, blocked in `GetMessage`, no CPU while idle) is a fourth thread of its own. `WM_HOTKEY` arrives there; it reads the Explorer selection with a cross-process COM call and posts to the wheel (`ShowClickMode`) or the HUD, so neither the hook callbacks nor the wheel thread ever wait for Explorer.
* **Only the gesture keys are ever read:** mouse move, left button, vertical wheel, Shift, Ctrl, Alt, Esc. Injected events (including our own mouse nudge) are flagged so `DragSession` can ignore them; touch and pen events are not flagged as injected. (The dev harness sets `MIKESHIFT_ACCEPT_INJECTED=1` so its synthetic input counts; never set in normal use.)
* **The wheel thread never converts and never blocks on anything slow.** Everything it touches is its own; other threads reach it through `WheelThread.Post`/`Wake` and read an immutable `WheelSnapshot` (UI Automation does).
* **The UI thread never converts.** `JobRunner.Enqueue` returns a job id immediately; the converter runs on the thread pool, then marshals the result (toast, chime, failure dialog) back. Interactive actions (Crop, Trim) call back into the UI through `IInteraction` (`UiInteraction`) and await the editor window.
* **Single instance:** `Program.Main` calls `AppInstance.FindOrRegisterForKey("mikeshift")` before any XAML starts; a second launch is redirected to the first, which pops its tray menu at the cursor.
* **A second kind of `MikeShift.exe` process:** `MikeShift.exe -Embedding` is not the tray app. COM starts it as the Explorer context menu's out-of-process server; `Program.Main` hands it to `ShellExtensionServer` before the single-instance check and before any WinUI starts, and it never touches the tray app's UI, hooks or wheel (§9).
* Converters are plain async methods on `MikeShift.Core` and take a `CancellationToken`; cancelling keeps outputs already written.
* **Classification must be fast** because the wheel is an empty disc until it is done. `Kind.Of` caches verdicts per (path, size, mtime) for the life of a drag; `Kind.CommonOf` classifies up to 16 files exactly, confirms a larger selection whose extensions all agree by sniffing a sample of 12, and sniffs any other large selection in parallel with early exit (500 JPEGs: about 20 ms).

## 3. Drag detection and the wheel

Windows has no readable global "drag pasteboard". The `IDataObject` of a drag lives inside the source's `DoDragDrop` loop and is only handed to a drop target. The design therefore detects the gesture from input, then puts a drop target under the cursor to receive the file list.

1. **Input monitor.** `SetWindowsHookEx` with `WH_MOUSE_LL` and `WH_KEYBOARD_LL` on a dedicated thread ([SetWindowsHookExW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowshookexw), [LowLevelMouseProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelmouseproc) which documents the `LowLevelHooksTimeout` behaviour, [LowLevelKeyboardProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc)). A missed button-up is covered by polling [GetAsyncKeyState](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getasynckeystate) (`AsyncInput`).
2. **State machine** (`DragSession`): `Idle → Pressed → Dragging → Armed → Released → Idle`. Pressed becomes Dragging after moving `SM_CXDRAG`/`SM_CYDRAG`; the **arm key** while Dragging arms (Shift by default, or Ctrl: `ArmKey`, chosen on first run, see item 8); the arm key held before the click still arms once the threshold is crossed (Explorer range select, or Ctrl-click to extend a selection). After button-up the wheel is dismissed 400 ms later if nothing was picked. The session emits commands (`ShowPending`, `PageToggle`, `HideSilently`, `DismissAfterRelease`, `Dismiss`, `End`) and knows nothing about windows.
3. **Pending wheel.** On Arm, the wheel window is shown centred under the cursor with only the disc, without activating it, then one zero-distance mouse move ([SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)) makes OLE re-hit-test even if the pointer is stationary (retried once after 90 ms). If no `DragEnter` arrives within 250 ms it was not a file drag (window move, text selection) and the wheel hides silently (so the bare disc can flash for up to 250 ms when Shift is pressed during a non-file drag).
4. **Hit surface.** A layered window's fully transparent pixels let the mouse, and OLE hit-testing, pass through, so the whole wheel square is painted with alpha ≥ 1 (`#01000000`). Never `WS_EX_TRANSPARENT`. Styles `WS_POPUP | WS_EX_LAYERED | WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE | WS_EX_TOPMOST` ([Window features](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features)), `WM_MOUSEACTIVATE` answers `MA_NOACTIVATE`. The window is created once and reused.
5. **Drop target.** A raw [`IDropTarget`](https://learn.microsoft.com/en-us/windows/win32/api/oleidl/nn-oleidl-idroptarget) registered with [`RegisterDragDrop`](https://learn.microsoft.com/en-us/windows/win32/api/ole2/nf-ole2-registerdragdrop) on the wheel window (wheel thread, STA). Every call is forwarded to [`IDropTargetHelper`](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nn-shobjidl_core-idroptargethelper) so Explorer's drag image keeps rendering over the wheel. `DragEnter` reads the file list cheaply (`CF_HDROP` or the shell ID list; see [Shell data scenarios](https://learn.microsoft.com/en-us/windows/win32/shell/datascenarios)); heavy formats are never requested. Virtual-file data (`CFSTR_FILEDESCRIPTORW`: Outlook attachments, zip-folder entries, phones) and URLs/pictures (browser images) get a "Save the file first" hint and `DROPEFFECT_NONE`; other data (selected text) gets no wheel.
6. **Never move the user's files.** The returned effect is always `DROPEFFECT_COPY & *pdwEffect`, never MOVE: a Shift-drag means MOVE to Explorer, and a MOVE result would delete the originals. On `Drop`, `CFSTR_PERFORMEDDROPEFFECT = DROPEFFECT_COPY` is also set. The harness asserts the originals are untouched, including with the real Explorer as the drag source.
7. **Explorer's own feedback.** While a tile is highlighted, `CFSTR_DROPDESCRIPTION` is set (a [DROPDESCRIPTION](https://learn.microsoft.com/en-us/windows/win32/api/shlobj_core/ns-shlobj_core-dropdescription) with `DROPIMAGE_COPY`, text "Convert to %1") so the native drag image reads "Convert to PNG". The format name is in the [shell clipboard formats](https://learn.microsoft.com/en-us/windows/win32/shell/clipboard).
8. **Modifiers.** `ModifierTracker` is fed by the keyboard hook and reconciled with `grfKeyState` on every `DragOver` (OLE re-calls `DragOver` when key state changes even without motion, and this covers elevated sources the hook cannot see). Keys (`ArmKey` + `ToolsKey`, `ToolsKeys.Normalize`): in **Shift mode** (default) a fresh Shift arms and returns to Formats and a fresh Ctrl switches to Tools; in **Ctrl mode** a fresh Ctrl arms and returns to Formats and a fresh Shift switches to Tools. The arm key can never also be the tools key (the stored `ctrl` default means "the other of the two"), Alt and the mouse wheel work in both modes, and in both a held key's auto-repeat is never a fresh press. After a silent hide only a fresh press of the arm key arms again. The hub and pill hints (`WheelModel.KeyHints`) and the tray text name the chosen keys; `FilterSelection` uses `ArmKeyAtMouseDown`, so a Ctrl-click that re-selects MikeShift's own outputs drops them like a Shift-click does.
    * **The Explorer-selection hotkey** is a second entry into the same click-mode wheel. `HotkeyService` owns one thread (STA, blocks in `GetMessage`, `RegisterHotKey(NULL, ...)` so `WM_HOTKEY` reaches its queue) that is separate from the hook thread and the wheel thread; on a press it asks `ExplorerSelection` for the selected files of the foreground window (a short cross-process COM call, which is why it never runs on the hook or wheel thread; classic `[ComImport]` interfaces, `IShellWindows` hand-written because the generated one wants `VARIANT`s), then calls `WheelController.ShowClickMode(paths, anchor)`: the wheel opens near the pointer (or the middle of the Explorer window), clamped to the work area like a drag wheel. No selection, or a foreground window that is not Explorer or the desktop: a toast. The default is Ctrl+Alt+Shift+Space; Settings can change it (capture the new chord; `HotkeyConflicts` warns or refuses) or turn it off, and shows when Windows reports the shortcut as taken (`HotkeyState.Taken`).
9. **Neutral zone and hit test** (`WheelGeometry`/`WheelModel`). The point where the drag entered the wheel is neutral until the pointer leaves it; sectors are offset by half a step; hub = no selection. Physical pixels throughout (PerMonitorV2); monitor chosen by `MonitorFromPoint`, wheel clamped to its work area (`WheelPlacement`).
10. **After a conversion**, `JobRunner` remembers the outputs; a Shift-click selection made within 20 s that includes them drops them (`DragSession.FilterSelection`), so you don't convert your own results.
11. **Click mode** (Convert Files…) is the same window and renderer, shown at the centre of the monitor under the pointer (for the Explorer hotkey and the right-click "More options…": at the pointer, `WheelPlacement.ForCursor`) and activated: arrow keys and Enter, mouse hover and click, Tab for the page, Esc or losing focus to close. UI Automation exposes the wheel as a list whose tiles are `ListItem`s ("Convert to PNG", "Compress") with `Invoke`, and raises focus/notification events so Narrator announces the highlighted tile (`WheelAutomation`).
12. **Known blind spot.** Windows blocks input hooks from seeing higher-integrity windows (UIPI, [security overview](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-securityoverview)), so drags from an elevated Explorer or app are invisible. See [the limitations](../limitations.md).

## 4. Wheel rendering

A normal XAML window cannot be a clean per-pixel-transparent, non-activating popup, so the wheel is a plain Win32 layered window drawn with Win2D into a premultiplied BGRA `CanvasRenderTarget`, read back, and pushed with [`UpdateLayeredWindow`](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-updatelayeredwindow) (`ULW_ALPHA`). Glass is a screen snapshot of the pixels under the wheel (a plain `BitBlt` without `CAPTUREBLT`, so neither the wheel nor Explorer's drag image is in it), blurred once with a Gaussian blur when the wheel appears, plus a tint; high-contrast mode skips the glass and uses system colours. Light/dark, accent colour and "animation effects" are read from the system at every show. Everything else (tray, toast, settings, editors) is ordinary WinUI 3. Geometry and animation numbers live in `Core/Interaction` (`WheelGeometry`, `WheelAnimation`, `WheelVisuals`), which is pure and unit-tested.

The wheel is visible about 30 ms after Shift is pressed (29 to 47 ms measured by the drag harness); the budget is 100 ms.

## 5. Memory behaviour

A tray app sits resident all day, so what it holds while idle matters more than keeping everything warm.

* The wheel's Win2D device (D3D11/D2D, the driver's heaps, the effect shaders) is by far the largest allocation (about 45 MB resident). `WheelRenderer` creates it on demand; the controller **releases it 15 s after the wheel hides**, compacts the managed heap and trims the working set (`MemoryTrim`, `SetProcessWorkingSetSize`).
* **A left-button press anywhere** re-creates it if it was released (`PrewarmIfCold`: device plus one throw-away frame, about 100 ms), long before a drag has moved and Shift is pressed, so the wheel latency does not change. While the device is warm, every press pushes the release time out.
* The blurred glass snapshot is dropped when the wheel hides; the 380 px pixel buffer goes with the device.
* A few seconds after an editor closes or a job finishes, `MemoryTrim.CompactSoon` does the same compaction (an editor holds a decoded preview and a lot of XAML state).
* The toast window is created 3 s after start-up (hidden; it costs one XAML window), Settings, Welcome, the tray flyout host and failure dialogs on first use. Codec probing (`Capabilities.Current`) runs once in the background at start-up. Nothing on the UI or OLE thread waits for it: the wheel's `DragEnter` uses `Capabilities.TryGetCurrent`, and if the probe has not finished it builds the first catalog from `Capabilities.Quick()` (no optional codec assumed, only the Word registry check and the Word permission) and replaces the tiles when `CurrentAsync` completes, keeping the page and re-hitting the pointer; the job runner reads the capabilities on its worker thread, and click mode builds its catalog off the UI thread.
* Measured on a Windows 11 x64 PC (Release, self-contained, 20 to 30 s after start): working set 198 MB → about 17 MB, private working set 94 MB → about 5 MB (private bytes, i.e. committed, about 57 MB). During a gesture the working set goes up again (a wheel on screen: about 115 MB private working set for a click-mode launch; an editor: about 190 MB) and is handed back afterwards. `MIKESHIFT_TRIM_MS` changes the 15 s (dev/test only).

| Zip | `System.IO.Compression` | UTC timestamps, reparse-loop and special-file refusal |

Every converter writes through `Naming` (a hidden `.name.guid.mikeshift-tmp` folder next to the target, then a move into place), so a failed job leaves no partial output, and hashes of the inputs are asserted unchanged in tests. Corrupt input is covered by a matrix test: truncated, misnamed and empty files through every offered action must end in `error: …` (exit 1) or a valid output, never a crash, a hang over 30 s (120 s for a legacy `.doc`, which goes through Word and its own 90 s kill switch), or a stray file. Word conversions run one at a time per process (instances started together stall each other), and the process-wide list of WINWORD.EXE processes is only used to find and kill the one instance a conversion started. The CLI ends with `TerminateProcess` after flushing its output (`FastExit`): the capability probe loads the GPU encoder stack (D3D/DXGI and the vendor driver), and tearing that down at normal process exit can fail-fast inside dxgi.dll on some PCs (observed at exit of the test host), which a caller would see as a crashed child instead of the exit code.

### 6.1 Conversion settings

Five settings, deliberately few: MikeShift does not try to be a format zoo with presets. `ConversionOptions` (Core) is an immutable record whose properties validate on `init` (so `with` is checked too) and whose defaults are the old constants:

| Setting | Values | Default | What reads it |
|---|---|---|---|
| Picture quality | whole number 50 to 100 | 90 | JPG, WebP and HEIC output of every image conversion, Resize and Crop of those formats, and PDF to JPG. PNG, TIFF, BMP and GIF are lossless or palette formats and ignore it. Strip EXIF keeps its own 0.95 (it is a fidelity tool). |
| Compress strength | Light, Medium, Strong | Medium | the picture Compress tool: longest side 4000 / 3000 / 2000 px and quality 0.75 / 0.6 / 0.45. PDF, video and audio Compress are unchanged. |
| Resize | 25, 50, 75 % | 50 | the Resize tool; each side rounds half up to whole pixels (at least 1). The tool's **title** follows ("Resize 25%", also the output suffix " 25%"), its **id** does not ("Resize"). |
| GIF length | 5, 10, 15, 30 s | 15 | `GifExporter.Export(..., seconds, ...)`: 10 frames a second, so at most `seconds * 10` frames. |
| Where converted files go | next to the original, or a folder | next to the original | `Naming.OutputFolder`, see below. |

* **Plumbing.** `ActionContext.Options` carries them; converters take a `ConversionOptions` parameter (the old signatures remain and mean "defaults"). `ActionCatalog.For(paths, caps, options)` only changes the Resize tile's name; the tile closes over its own percentage, so title, suffix and result can never disagree. `ActionCatalog.Find` matches the title, else the stable id ("Resize 25%" still finds the tool after the setting changed to 75 %, and plain "Resize" finds it too); rankings (the Explorer menu) use the id.
* **The output folder** is applied in one place: `ActionDef.Run` wraps every action and sets `Naming.OutputFolder` (an `AsyncLocal`, restored in `finally`) for the duration of the run, so every converter, Merge and Zip land in the chosen folder without knowing about it. `Naming.CommitAsync` treats a chosen folder that is missing (it is not recreated behind the user's back) or not writable exactly like an unwritable original folder: Downloads, flagged in `ActionOutput.UsedDownloadsFallback`; `ActionResult.ChosenFolder` lets the toast say "In Converted" or "In Downloads (Converted isn't available)" instead of "Next to the original".
* **Storage.** `Preferences` keys `convQuality`, `convCompress`, `convResize`, `convGifSeconds`, `convOutputFolder` (plain strings in `LocalSettings` or `settings.json`); `Preferences.Conversions` builds the record with `ConversionOptions.FromStored`, which falls back to the default one setting at a time, so older or hand-edited files never break a conversion. `JobRunner` reads it when a job starts; the wheel and the picker read it when they build their tiles.
* **Settings window.** A "Conversions" group of `SettingsCard`s after General: a slider (steps of 5, the value written next to it), three combo boxes whose descriptions follow the choice (`ConversionCopy`), and an expander for where files go (radio buttons, the common folder dialog `FilePicker.PickFolder`, a warning when the folder cannot be used). Screenshot: [settings.png](../images/settings.png).
* **Command line.** `--quality N`, `--compress light|medium|strong`, `--resize 25|50|75` (or `--run "Resize 25%"`), `--gif-seconds N`, `--out DIR` (must exist). One option has no Settings card: `--max-size MB` (1 to 2000, or `--run "Fit 8 MB"`) sets `ConversionOptions.FitMegabytes`, which replaces the two fixed video Fit tiles (10 and 25 MB) with one of that size, the same title/id pattern as Resize (id "Fit"). The wheel and the Explorer menu never set it. The CLI never reads the Settings window's choices: a script behaves the same on every PC. A bad value, or a title and `--resize` that disagree, is a usage error (exit 2).
* **The Explorer menu** only needs the Resize percentage for its wording: the tray app writes `shell-options.txt` next to `shell-capabilities.txt` whenever a conversion setting changes (the folder is deliberately not in it), and the extension process re-reads it when it changes. The job itself always runs in the tray app with the real options.

## 7. Packaging

* **MSIX**, built by the Windows App SDK tooling (`WindowsPackageType=MSIX`), one package per architecture (x64, ARM64), **IL-trimmed** and **self-contained .NET**: the .NET 10 runtime ships inside the package (an MSIX cannot depend on a machine-wide .NET). `scripts/release.ps1` writes each architecture as its own `.msix` (`MikeShift_<ver>_x64.msix`, `_arm64.msix`: what a user downloads for their PC), combines both into one `.msixbundle` with `makeappx bundle` ([MakeAppx](https://learn.microsoft.com/en-us/windows/msix/package/create-app-package-with-makeappx-tool)), signs all of them with `signtool` if given a certificate, and lists all of them in `SHA256SUMS.txt`.
* **Two flavours** (`release.ps1 -Flavor sideload|store|all`, i.e. `-p:WindowsAppSDKSelfContained=true|false`). *sideload* (the default) carries the Windows App SDK in the package: 44.9 MB (x64) / 43.6 MB (ARM64), nothing to install first, the safest file to hand to someone. *store* depends on the shared framework package `Microsoft.WindowsAppRuntime.2` (the manifest gets `<PackageDependency Name="Microsoft.WindowsAppRuntime.2" MinVersion="2.5.1.0" Publisher="CN=Microsoft Corporation, ...">`, added by the Windows App SDK build): 23.3 MB / 22.5 MB. The Store installs the framework itself; a sideloaded store-flavour package needs it installed first (Microsoft's `WindowsAppRuntimeInstall-<arch>.exe`, or `Add-AppxPackage -DependencyPath`; the build leaves Microsoft's framework `.msix` files in `AppPackages\<flavour>\...\Dependencies\`). Both flavours run the same trimmed managed code; they differ only in where WinUI's native files come from. The release script builds each flavour and architecture from a clean app `obj\`/`bin\`, because the Windows App SDK mode changes the manifest and the file list and an incremental build would mix the two.
* **Windows App SDK by component.** The app references `Microsoft.WindowsAppSDK.Base`, `.Foundation`, `.InteractiveExperiences` and `.WinUI` (2.5.1 line) instead of the `Microsoft.WindowsAppSDK` metapackage, which also drags in the on-device AI, ML (ONNX Runtime + DirectML), Search, Widgets and DWrite components that MikeShift never calls. `H.NotifyIcon.WinUI` depends on the metapackage, so it stays in the restore graph; the metapackage and those components are referenced with `ExcludeAssets="all"` (see the comment in `MikeShift.App.csproj`), which keeps them out of the output and the MSIX. Effect: bundle 304.8 MB → 256.8 MB, per-architecture package 154.6 → 130.3 MB. When bumping the Windows App SDK, update the component versions in `Directory.Packages.props` to what the new metapackage's `.nuspec` lists, and check that no `onnxruntime.dll`/`DirectML.dll` reappears in the output.
* **One `Application` entry** in `Package.appxmanifest`: `App` (the tray app, `MikeShift.exe`). The `mikeshift.exe` command on PATH is an app execution alias ([uap5:AppExecutionAlias](https://learn.microsoft.com/en-us/uwp/schemas/appxpackage/uapmanifestschema/element-uap5-appexecutionalias)) on that entry whose `Executable` is `MikeShift.Cli.exe`, with `desktop4:Subsystem="console"`, so stdout, stderr and the exit code reach the terminal. The console alias requires `desktop4:SupportsMultipleInstances="true"` on the entry; the tray app keeps itself single-instance in `Program.cs`. The CLI is not an `Application` of its own because the Microsoft Store rejects an entry with `AppListEntry="none"` (a "headless app") unless the app has a waiver, and a visible entry would add a console tile to the Start menu.
* **The CLI shares the tray app's runtime.** Both executables sit in the package root. The CLI's assembly is called `MikeShift.Cli` (not `mikeshift`) because file names on Windows are case-insensitive and the tray app's `MikeShift.exe`/`MikeShift.dll`/`MikeShift.runtimeconfig.json` would collide with `mikeshift.*`; the `mikeshift.exe` command is only the alias name, which does not have to match the file. The app project (`BundleMikeShiftCli` target in `MikeShift.App.csproj`, under the "Packaging" comment) publishes the CLI self-contained and takes the files that make an exe a self-contained app (`MikeShift.Cli.exe`, `.dll`, `.runtimeconfig.json`, `.deps.json`) into the package root; the rest of the runtime, Core, PdfSharp, SkiaSharp and the Windows SDK projection are the app's own copies. A separate self-contained copy had cost about 51 MB per architecture. In an untrimmed (dev) build the target `VerifyBundledCliSharesRuntime` proves that by hashing every other file of the CLI's publish against the app output and failing the build if one differs. In a **trimmed package** two separately trimmed copies of the shared assemblies would differ, so the CLI is trimmed *with* the app: `AddBundledCliToTrimInputs` hands the untrimmed `MikeShift.Cli.dll` to the app's ILLink run as an extra input and entry-point root, the one trimmed set in the package therefore keeps everything the CLI uses, the linked `MikeShift.Cli.dll` comes out of that run, and `MikeShift.Cli.deps.json` is derived from the app's (`WriteBundledCliDepsFile`: the host only treats the exe as self-contained if a deps.json lists exactly the files that are there). `VerifyBundledCliTrimmedSharesRuntime` checks that every file of the CLI's own publish is in the package and that the CLI's `runtimeconfig.json` settings are all in the app's. Opt out of the CLI with `-p:BundleCli=false` for faster inner-loop builds.
* **IL trimming** (`Trimming.props`, imported by the App and CLI projects; `-p:MikeShiftTrim=false` for an untrimmed package). The MSIX tooling already supports it: for an exe project it packages the *publish* item list (`__GetPublishItems`), so `PublishTrimmed=true` on the package build (`-p:GenerateAppxPackageOnBuild=true`) makes ILLink run and the trimmed assemblies go into the MSIX. It is set only for package builds (a plain `dotnet build` stays fast), while the trim analyzers (`EnableTrimAnalyzer`) run on every compile with `TreatWarningsAsErrors`. `TrimMode=full`. Saved 80.1 -> 44.9 MB (x64): `System.Private.CoreLib` 15.3 -> 3.1 MB, `Microsoft.Windows.SDK.NET` 25.1 -> 0.8 MB, `Microsoft.WinUI` 7.0 -> 1.0 MB, `System.Private.Xml` 7.4 -> 0.7 MB, OpenXml 7.6 -> 5.1 MB. How the hazards were handled (the trimmer hazards and how each is handled):
  * `settings.json` is read and written through a source-generated `JsonSerializerContext` (reflection JSON is off in trimmed apps); Word automation no longer uses `dynamic` (the C# runtime binder is reflection) but `CoCreateInstance` and `Type.InvokeMember`, which on a COM object is an `IDispatch` call; `IDropTargetHelper` is created with `CoCreateInstance`, not `Activator.CreateInstance(Type.GetTypeFromCLSID(...))`.
  * Classic `[ComImport]` interop needs `BuiltInComInteropSupport=true` (trimmed apps lose it otherwise). `MikeShift` and `MikeShift.Core` are trim roots (`TrimmerRootAssembly`), so the COM interfaces declared there (hand-written ones and CsWin32's) stay whole; the trimmer's advisory IL2050 ("COM interop cannot be guaranteed") is suppressed on the few callers with that justification.
  * **COM interfaces in the framework and in libraries lose methods unless protected**, which shifts their vtables: the BCL's `ComTypes.IDataObject` lost 5 of its 9 methods and the first Shift-drag crashed the app (access violation in `QueryGetData`; found only by running the real drag harness, invisible to unit tests and scenes). `tools/ComInterfaceScan.cs` (run by the build with `dotnet run --file`) writes a root descriptor that preserves every `[ComImport]` interface of the linker's inputs whole (`required="false"`: when used), and after the link it compares each surviving interface with its input and fails the build if one lost a method.
  * The WinRT projections' "unused interfaces" optimisation is switched off (`_TrimmerUnusedInterfaces=false`): without it, classes derived from WinUI controls (`SettingsCard : ContentControl`) lost the `IxxxOverrides` interfaces the native XAML calls back into and Settings and the trim editor failed to load.
  * Two ILLink warnings are accepted, each attached to the framework code that raises it and not with a project-wide `NoWarn` (`tools/ILLink.FrameworkSuppressions.xml`, passed to the linker as link-attributes by `Trimming.props`): IL2081 inside `Microsoft.Windows.SDK.NET`/`WinRT.Runtime` (70 of them, in the generic WinRT collection fallbacks, none reached by this app; the Windows SDK projection used for MediaTranscoder, Windows.Data.Pdf, StartupTask... is exercised by the CLI suites; without them the assemblies' IL2104 "produced trim warnings" disappears too) and the framework's own IL2026 on `ComActivator.GetClassFactoryForTypeInternal` for built-in COM. A new IL2026/IL2104/IL2xxx from `MikeShift.*` or any other assembly fails the trimmed build (checked with a temporary `JsonSerializer.Serialize` call in Core, `#pragma`-hidden from the compile-time analyzer so only the linker can see it).
* **Not taken.** ReadyToRun would make the package larger. Satellite resource languages are limited to English (`SatelliteResourceLanguages`), PDBs are not packaged, each package carries the native assets of its own architecture only. Remaining dead weight: `libSkiaSharp.dll` (12 MB, used for WebP), the runtime pack's `Microsoft.DiaSymReader.Native`, `msquic` and the standalone GC libraries (about 1.9 MB compressed per architecture), and the debugger/dump DLLs (`mscordaccore`, `mscordbi`, about 1.7 MB), which are kept so crash dumps stay analysable.
* **Explorer right-click entry** (§9): the `App` application also declares a `windows.comServer` (`com:ExeServer`, `MikeShift.exe -Embedding`) and a `windows.fileExplorerContextMenus` registration for files and folders. No new files in the package, no native DLL: the extension is the same trimmed exe on the same runtime, so both flavours and both architectures are unchanged (x64: sideload about 45 MB, store about 23 MB). `desktop5:ItemType` needs Windows 10 1809, which is the package's minimum.
* **Open at Login:** the manifest's `windows.startupTask` (`MikeShiftStartup`, disabled by default), driven by [`StartupTask`](https://learn.microsoft.com/en-us/uwp/api/windows.applicationmodel.startuptask); it appears in Settings → Apps → Startup, where the user can also turn it off. Unpackaged dev runs use the HKCU Run key instead.
* **Single instance:** [`AppInstance`](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.windows.applifecycle.appinstance) (see §2).
* **Signing:** the manifest Identity is the Microsoft Store identity from Partner Center, and the Store signs Store packages; for sideloading, `packaging/make-dev-cert.ps1` creates a self-signed certificate whose subject is the manifest Publisher ([creating a signing certificate](https://learn.microsoft.com/en-us/windows/msix/package/create-certificate-package-signing)). Long paths are enabled by the application manifests.
* **CI:** `.github/workflows/ci.yml` builds and tests on `windows-latest`, then runs `scripts/release.ps1 -Flavor all` (clean trimmed builds of both flavours and both architectures) and uploads the unsigned `.msix` files, bundles and `SHA256SUMS.txt`.

## 8. Developer switches

The tray app has a set of switches that exist for the drag harness, the screenshot scripts and manual testing. Some of them weaken the product (`MIKESHIFT_ACCEPT_INJECTED` lets any program's `SendInput` drive the wheel), so they are all read through one class, `MikeShift.App/DevSwitches.cs`, and honoured only when **`DevSwitchPolicy.IsEnabled`** says so:

| Build | Honoured? |
|---|---|
| Debug | always |
| Release, unpackaged, started with `--dev` | yes |
| Release, unpackaged, no `--dev` | no |
| Release, packaged (MSIX) | never, even with `--dev` |

So an installed MikeShift ignores every `MIKESHIFT_*` variable and every dev flag; `--smoke-test` is not a dev switch (CI uses it) and always works. A Release build under test is started as `MikeShift.exe --dev ...`; `tools/DragHarness` and `scripts/capture-scene.ps1` pass `--dev` themselves. Note that the drag harness therefore only works against a Debug build, or an unpackaged Release build, not against an installed package.

| Switch | Effect |
|---|---|
| `MIKESHIFT_ACCEPT_INJECTED=1` | input synthesised by `SendInput` counts as real (the harness drives drags with it) |
| `MIKESHIFT_NO_HOOKS=1` | no global input hooks (dev scenes next to a real instance) |
| `MIKESHIFT_NO_SINGLE_INSTANCE=1` | skip the single-instance redirect |
| `MIKESHIFT_SETTINGS_PATH` | another settings file (unpackaged runs) |
| `MIKESHIFT_LOG`, `MIKESHIFT_TRACE=1` | another log file; interaction stage lines in the log (always on in Debug) |
| `MIKESHIFT_HINTS_FILE` | another file for the wheel-hint counter |
| `MIKESHIFT_PICKER_FOLDER` | Convert files… starts in this folder |
| `MIKESHIFT_THEME=light\|dark\|hc` | force the theme (`hc` only for the wheel) |
| `MIKESHIFT_ANIMATIONS=0` | behave as if animation effects were off |
| `MIKESHIFT_DPI_SCALE=1.5`, `MIKESHIFT_TEXT_SCALE=1.4` | pretend every monitor's scale, or the OS text size |
| `MIKESHIFT_CAPS=no-heif,no-hevc,no-av1,no-webp` | pretend those Windows extensions are missing (`Capabilities.Override`, remove-only): shows the "Get HEIF" tile and the welcome codec card on a PC that has them. `no-wic-webp` (via `CapabilityOverrides.Apply`) makes every product WIC decode of a WebP behave as if Windows had no WebP decoder, so the SkiaSharp fallbacks (image converters, Image to PDF, crop editor) run on a PC that has the WebP Image Extension |

## 9. Explorer right-click entry ("Convert with MikeShift")

Windows 11's modern context menu (and Windows 10's menu) can carry one entry per packaged app, implemented as an `IExplorerCommand` and declared in the package manifest. MikeShift's entry is **one top-level command with a one-level submenu**: the few most useful actions for the selection, then "More options…", which opens the click-mode wheel. Windows 11 shows one top-level entry per app, so the submenu is the only way to offer several actions; a submenu inside the submenu is not possible (Explorer does not support sub-commands of sub-commands), which is why "More options…" opens the wheel instead of a second menu level.

### 9.1 Process model

```
 explorer.exe (UI thread)               MikeShift.exe -Embedding                       MikeShift.exe (tray app)
 ------------------------               ------------------------                       ------------------------
 right-click ── CoCreateInstance ─────► ClassFactory ► ConvertCommand
 GetState/GetTitle/GetIcon(items) ────► ShellSelection.Read: names of up to 500 items,   (running all day, WinUI,
 EnumSubCommands()                ◄──── ContextMenuPlanner over the cached capabilities    JobRunner, wheel)
 click "Convert to PNG": Invoke(items)─► read every path, return at once; then a
                                         background task: ShellPipeClient ── named pipe ──► ShellBridge
                                         (current user only, local)                          ActionCatalog.For(paths): exact
                                         tray app not running? ActivateApplication starts    JobRunner.Enqueue  (same toast, naming,
                                         it (like the Start menu) and the send is retried    originals untouched)  or the wheel
```

* **Out of process on purpose.** Explorer is the user's shell: a managed runtime inside `explorer.exe` could never be unloaded, pauses with its garbage collector, and a bug in it would take the desktop with it. The package manifest declares a `com:ExeServer` (`MikeShift.exe`, argument `-Embedding`), so COM starts a separate process on the first right-click and Explorer only holds proxies. Microsoft's own sample uses a native DLL in a `com:SurrogateServer` (dllhost.exe loads it); an exe server needs no native DLL, no C++ toolchain and no second runtime, and it is the very exe that the trimming, signing and both flavours already cover. Explorer activates a `com:ExeServer` for `IExplorerCommand` (`CoCreateInstance` with `CLSCTX_LOCAL_SERVER`): verified on Windows 11 build 26300, sideload and store flavours.
* **The server is not the tray app.** `Program.Main` checks for `-Embedding` first thing and returns `ShellExtensionServer.Run()`: no WinUI, no single-instance check, no hooks, no wheel. It registers the class factory with `CoRegisterClassObject(REGCLS_MULTIPLEUSE)` on an MTA thread (so Explorer's calls never queue behind one another), keeps serving the following right-clicks from the same process and **exits after 10 idle minutes** (`ServerLifetime`; never while a call or a send is in flight). Measured: about 14 MB private, 46 MB working set while alive; cold start (first right-click after it exited) about half a second, then a few milliseconds per menu.
* **COM without built-in marshalling.** Every interface here is `[GeneratedComInterface]` and every object `[GeneratedComClass]` (`StrategyBasedComWrappers`), declared with all methods in vtable order; nothing relies on the runtime's classic COM interop, so the IL trimmer cannot remove a method and shift a vtable (the problem described in §7). Methods return HRESULTs (`[PreserveSig]`) and never throw.
* **Fast on Explorer's UI thread.** The calls Explorer makes while it builds the menu do names only: the selection's file-system paths (`IShellItem::GetDisplayName`), `Kind.ByExtension` (no file access, no decoding), the capabilities cached by the tray app, no DOCX/ODT probing. A plan takes 0.3 to 1.5 ms (`shell-log.txt` has one line per menu); four COM calls for a menu take 3 to 8 ms warm.
* **Local only.** The pipe is `mikeshift-shell-<user SID>`, created with `PipeOptions.CurrentUserOnly`; `ShellRequest` is a length-prefixed binary message (verb, action title, paths, and for "More options…" the pointer position; magic `MSH2`) with hard bounds; the tray app validates every path (fully qualified) and **resolves the action itself**, by title (or stable id), from the exact `ActionCatalog.For(paths, capabilities, options)` of the selection it received. The extension can only ask for what the wheel would offer. No network code was added.

### 9.2 What the menu offers

`ContextMenuPlanner.Build` (Core, unit-tested) turns a selection into the lines:

* Classification is **by extension** (`Kind.ByExtension`), folders (from `SFGAO_FOLDER` without `SFGAO_STREAM`) count as "other". A selection of one category gets that category's actions in a fixed popularity order: images `JPG, PNG, Merge PDF, PDF, Compress, Resize, WebP, HEIC, …` (ranked by `ActionDef.Id`, so the line reads "Resize 25%" or whatever the setting says, in the same place); PDFs `Merge, Compress, PNG, JPG, Split, TXT`; video `MP4, MP3, GIF, Compress, Fit, …` (Fit is the 10 MB tile); audio `MP3, M4A, WAV, Compress, …`; documents `PDF, DOCX, TXT, HTML, …`. Only actions the catalog would offer count (capabilities, "already that format", at least two items for Merge). The first **5** become lines (`Convert to JPG` for a format, the title for a tool, "Merge PDFs"/"Split pages" worded for a menu), **Zip** is always the last line, then "More options…".
* A folder, a mixed selection, unknown files: `Zip` and "More options…". More than 500 items: `Zip` and "More options…" only, without classifying anything (see below: Explorer never hands over that many while building the menu).
* The command is hidden when the selection has an item that is not a file-system item (a virtual folder, an MTP device).
* Capabilities: the tray app writes `shell-capabilities.txt` (the codec flags, one `Name=True` line each) into the real package data folder after its start-up probe and whenever the Word setting changes; the server re-reads it when it changes. Without the file (the very first right-click on a fresh install, before the tray app has probed) the conservative `Capabilities.Quick()` is used, which only hides what depends on optional codecs.
* **HEIC/HEIF/AVIF without their decoder.** The menu does not decode anything, but the cached capabilities say whether Windows can open these formats. When every selected file has an extension that depends on the same missing extension (`CodecHelp.ForExtensions`), the submenu is **"Get the free HEIF extension"** (or the HEVC / AV1 line) and Zip, instead of formats that would all fail. Picking it sends `Run "Get HEIF"`; the tray app asks `CodecHelp.ResolvePick` with its live capabilities (same rule as the menu) and opens the Store page; if the extension has been installed since the menu was drawn, the title is resolved in the ordinary catalog and the wheel opens. Until the tray app has written its first capability cache the menu cannot know, and offers the ordinary formats rather than telling everyone to install what they may already have.
* The exact check of every other line runs when it is clicked; if the action does not fit the selection after all, the tray app opens the wheel with what *is* possible (Zip) instead of failing.
* **"More options…"** sends the pointer position the extension read in `Invoke` (`GetCursorPos`), so the click-mode wheel opens at the pointer (clamped to the work area) even when the tray app had to start first and the pointer has moved on.

### 9.3 What Explorer does (measured on Windows 11 build 26300)

* `EnumSubCommands` has **no parameter**: the submenu has to be the one for the selection of the last `GetState`/`GetTitle` call, so `ConvertCommand` remembers the plan of the last items array (`ReferenceEquals` on the proxy).
* **For a big selection Explorer passes only 16 items while it builds the menu** (600 files selected: `GetCount` returned 16; `Invoke` then received all 600 and Zip packed 600). So the menu of a big selection is built from Explorer's 16-item sample; which 16 is Explorer's business (a selection of 18 JPEGs and 4 PDFs gave a sample with both kinds, so only Zip). The planner's 500 cap therefore never triggers through Explorer; it remains for hosts that pass more.
* The modern flyout does not draw a separator for a sub-command flagged `ECF_ISSEPARATOR`; the classic menu does. Harmless.
* **"Show more options"**: on this build the classic menu **also lists** the packaged `IExplorerCommand` entry (same submenu; Shift + right-click opens that menu directly). Microsoft's documentation says the classic menu is only for legacy handlers, so on other Windows 11 builds the entry may be missing there (see [the limitations](../limitations.md)). The manifest-level alternative, `desktop9:FileExplorerClassicContextMenuHandler`, was tried: it only accepts a class declared as a `com:SurrogateServer` (a native DLL), the package fails validation (0x80080204) when it points at an exe server, and a build like 26300, which already lists packaged commands in the classic menu, would show the entry twice (PowerToys, which registers both ways, appears twice in that menu on that build), so it is not used.
* The modern menu loads the icon from the path `GetIcon` returns; the app's `.ico` inside the (access-restricted) package folder works.

Unit tests: `ContextMenuPlanTests` (lines per selection, order, caps, labels, no disk access), `ContextMenuSettingsTests` (Resize wording and ranking by id, the HEIC/AVIF "Get ..." lines, menu, catalog and tray agreeing, the pointer position in the request), `ShellRequestTests` (message and capability-cache round trips, garbage input), `ManifestTests` (the CLSID, the `-Embedding` argument and the two item types agree between manifest and code).
