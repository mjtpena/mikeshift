# Hardening: Word opt-in, a flaky move, narrower trim suppression (2026-10-24)

Build: `feature/windows-port` @ `90e4c34` plus this branch. .NET SDK 10.0.300, Windows 11 26300, x64. Microsoft Word is installed on this PC (and one Word that was already open was left alone throughout).

## 1. Word is off by default

* Setting: Settings -> "Use Microsoft Word for Word documents" (default Off); CLI: `--use-word`, per run. `Capabilities.WordCom` is now "installed and allowed"; `WordInstalled` is the registry check.
* Off: DOCX to PDF uses the built-in converter; `.doc` offers Zip only; the wheel and click mode say "Turn on Microsoft Word in Settings to convert .doc files" (a caution pill, the same one as "Save the file first").
* `scripts/verify-offline.ps1 -SkipApp` against the Debug CLI, no `--use-word`: **265 CLI processes** (221 x exit 0, 16 x exit 1, the same documented refusals), 253 distinct `MikeShift.Cli` PIDs sampled every 50 ms, **0 TCP/UDP endpoints owned by MikeShift, 0 WINWORD.EXE processes started during the run, 0 sockets owned by Word**, cmdlet cross-check 0 entries, no DNS cache entry added. Before this change the same script measured 7 Word processes and 234 sockets to Microsoft (port 443). The script now fails when a Word process starts without `-UseWord`, and `-UseWord` measures the opt-in path.
* Tests: catalog (Word installed but not allowed -> Zip only, allowed -> the old tiles), converter (DOCX to PDF with Word installed and not allowed: no new WINWORD during the conversion, PDFsharp producer in the file; `.doc` refused with the Settings hint), wheel pill text and its conditions, `CliRunner` (`--use-word` honoured only per run, whatever caps the caller passes), `WithWord`, defaults. In the CLI assembly `WordWatch` polls the machine's WINWORD list every 25 ms around a real `MikeShift.Cli.exe` run: none appears without `--use-word` (docx to PDF, and a `.doc`), and the Slow positive control proves the watcher sees one with `--use-word`. A named semaphore (`WordLock`) keeps the Word tests of the two test assemblies from overlapping (they run in parallel under `dotnet test MikeShift.sln`; without it the watcher caught the other assembly's Word).

## 2. The flaky PDF-to-image test

* `Pages_to_images_have_the_right_count_size_and_content` never failed in 12 full-solution runs, 18 parallel runs of `PdfIntegrityTests` (6 processes at once, three rounds, one with a clean build running beside them) and 6 parallel runs of everything matching Pdf/Integrity, so its own message was not captured here.
* What the loop did catch (run 2 of 12, while a Release package build was running): `IntegrityCliTests.Pdf_actions_through_the_exe` -> `mikeshift --run JPG exited 1: error: Access to the path '...\.doc pages.<guid>.mikeshift-tmp' is denied.` Same operation as the flaky test (a 3-page PDF written to a `doc pages` folder, "PNG" or "JPG").
* Root cause: `Naming.CommitAsync` renames the temp folder into place. A scanner (antivirus, search indexer) that has just-written page images open without delete sharing makes `Directory.Move` fail with ERROR_ACCESS_DENIED, which .NET reports as a plain `IOException`; only sharing violations (32/33) were retried. A new `NamingTests` case holds a file inside the folder open for 300 ms and reproduces that exact message without the fix and passes with it.
* Fix: the final move also retries access denied (0.1, 0.25, 0.5, 1 s; the original exception propagates if it persists), only there (the folder was just created and written, so a denial can only be a passing one).
* Honest limit: I could not make the originally reported Core failure itself recur, so that it is the same cause is likely (same operation, same folder move, load-dependent, passes alone) but not proven. Word is no longer started by the suite's document tests by default, which also removed a source of machine load during the PDF tests.
* After the fix: **11 of 11 consecutive full `dotnet test MikeShift.sln` runs green** (Core 2112 passed / 12 skipped, CLI 79 passed / 3 skipped each time), then `MIKESHIFT_SLOW=1`: Core 2167 / 2167, CLI 82 / 82.

## 3. Trim warnings

* `Trimming.props` no longer has `NoWarn IL2104;IL2026`. `tools/ILLink.FrameworkSuppressions.xml` (passed to ILLink as link-attributes) attaches `UnconditionalSuppressMessage` to `System.Private.CoreLib` `ComActivator.GetClassFactoryForTypeInternal` (IL2026) and module-scope IL2081 to `Microsoft.Windows.SDK.NET` and `WinRT.Runtime` (so neither produces IL2104). Attribute-only IL2104 suppression did not work (the warning has an assembly origin), IL2081 at module scope did.
* Proof: a temporary `JsonSerializer.Serialize(object)` in `MikeShift.Core`, wrapped in `#pragma warning disable IL2026` so only the linker sees it: with the old props the trimmed build **passed**; with the new ones it **fails** (`Trim analysis error IL2026: MikeShift.Core.TempTrimProbe.Reflective(Object): ...`). The probe was removed afterwards.
* `scripts/release.ps1 -Flavor sideload -Platforms x64`: succeeds, 44.9 MB (as before), the one existing `mspdbcmf.exe` warning, no IL2xxx. `mikeshift` CLI suite against that package's unpacked `MikeShift.Cli.exe` (`MIKESHIFT_CLI_EXE`, `MIKESHIFT_SLOW=1`): **82 / 82**, including the Word positive control through the trimmed `WordInterop`.
