# Limits and Windows-specific differences

Everything that works differently from the macOS original, depends on the machine, or is refused. Where a limit shows up as a message, the wording below is the app's own (the CLI prints it as `error: …`, the app in the toast or a dialog). Everything in the PLAN is built; nothing here is "planned" any more except where a line says so.

## Not offered on Windows

| Item | Why |
|---|---|
| **MOV output** (video) | Media Foundation has no QuickTime muxer. MOV files can be read; they convert to MP4, M4V, WMV, GIF, M4A or MP3. |
| **AVIF output** (images) | Windows has no AVIF encoder and none is bundled. AVIF files can be read when the free "AV1 Video Extension" is installed. |
| **Folders in Convert Files…** | The Windows file dialog cannot select files and folders in one dialog (turning on folder picking turns files off), so Convert Files… picks **files** only. To convert or zip a folder, Shift-drag it from Explorer. |
| **Ctrl+O for Convert Files…** | The tray menu's **Convert Files…** has an access key (press the underlined letter) but no Ctrl+O shortcut. PLAN §1.1 asked for Ctrl+O, but a global Ctrl+O would hijack the Open command of whatever program has focus, so this is a deliberate deviation. |
| **A fixed activation key** | Not one key for everyone: first run asks "How do you want to open the wheel while dragging?" (**Shift** or **Ctrl**, both offered equally; Settings changes it). The other of the two switches to Tools. Shift stays the default because Shift-drag is rare in daily use; its cost is that Explorer reads Shift-drag as *move* when you let go over an ordinary folder (MikeShift always answers *copy* on its own wheel, so the wheel is safe), which Ctrl avoids. Ctrl has its own cost: Ctrl-click is how people extend a selection, so a Ctrl that is still held when a drag starts arms the wheel. |
| **The Explorer hotkey is a global shortcut** | **Ctrl+Alt+Shift+Space** (changeable, or "None") opens the click-mode wheel for the files selected in File Explorer or on the Desktop. A shortcut registered with Windows (`RegisterHotKey`) goes to MikeShift *instead of* the program in front, and only one program can own it: the shorter Ctrl+Alt+Space was already taken on the development PC (the Claude desktop app uses it; Windows error 1409), Ctrl+Shift+Space is Word's non-breaking space and Excel's "select the whole sheet", and shortcuts with the Windows key are Windows'. If Windows refuses the shortcut, Settings says another program owns it and the hotkey does nothing until you choose another. It reads the selection of the *foreground* Explorer window (with tabs, the tab that is showing); an Explorer window running as administrator probably cannot be asked from a normal MikeShift (not tested), search results and libraries should work because their items are real files (not tested either), and "This PC", the Recycle Bin and phones (items without a file-system path) count as no selection. |
| **Alt as the default tools key** | Left Alt+Shift is Windows' default input-language hotkey, and releasing Alt can send a menu-activation message to Explorer. The default is Ctrl (plus a mouse-wheel tick); Alt remains selectable in Settings with that caveat. |
| **Automatic updates, a Store listing, public signing** | Not built. "Check for Updates…" just opens this project's releases page (github.com/mjtpena/mikeshift/releases) in your browser; the app never goes online itself. Sideloading needs a certificate you trust (see README). |
| **Dithered GIFs** | GIF export reduces each frame to at most 256 colours (a per-frame median-cut palette) with no dithering, so gradients show banding. It is also limited to 10 fps and 480 px on the long side, and to the first 15 s unless Settings (or `--gif-seconds`) says 5, 10 or 30 s. |
| **Lossless video Trim** | Video Trim always re-encodes (MP4 for most sources, WMV for WMV sources): cutting without re-encoding can only start on key frames, which gives the wrong start. Only WAV and AIFF audio is cut losslessly; other audio is re-encoded to M4A. |

## Depends on what is installed on the PC

The app probes the machine at startup and hides tiles that cannot work, rather than offering them and failing. The probe takes a fraction of a second on a warm PC and longer on a cold one; a Shift-drag that starts before it has finished shows a reduced set of tiles for a moment (no HEIC, WebP or media tiles) and then fills in the rest while you are still dragging.

| Capability | Needed for | What happens without it |
|---|---|---|
| **HEIF Image Extensions + HEVC Video Extensions** (Microsoft Store; the HEIF extension is free; "HEVC Video Extensions" is sold by Microsoft, and the Store's "HEVC Video Extensions from Device Manufacturer" listing that MikeShift links to is the free one) | HEIC **output**; reading HEIC photos | **HEIC encode depends on both extensions**: without them there is no **HEIC** tile and Compress falls back to PNG for sources that would otherwise become HEIC. A HEIC photo that Windows cannot decode is not a dead end any more: it is still not an image to MikeShift, but the wheel (and Convert files…) shows one **Get HEIF** tile (or **Get HEVC** when only that decoder is missing) next to Zip, with the pill "HEIC photos need the free HEIF extension"; the tile opens that extension's Microsoft Store page instead of converting. A conversion that hits it anyway (command line, a job) fails with "Windows can't open HEIC photos yet. Install the free "HEIF Image Extensions" from the Microsoft Store, then restart MikeShift." and the failure dialog has a **Get the extension** button. The welcome window checks at first run and offers the same links; after installing, restart MikeShift (it probes once at start). If both extensions are present and a HEIC still will not open, the file is damaged and only Zip is offered. Only `.heic`/`.heif` and `.avif` get this treatment, by extension: a misnamed file does not. |
| **AV1 Video Extension** (free) | Reading AVIF | AVIF files Windows cannot open show the same single tile (**Get AV1**) next to Zip, and the same advice when a conversion fails. |
| **WebP Image Extensions** (free) | Reading WebP via Windows | SkiaSharp (bundled) decodes WebP as a fallback; WebP **output** always works (SkiaSharp), a Windows-only extra. |
| **HEVC / VP9 / AV1 decoders** | Reading such videos | The video is not recognised (Zip only) or fails with "Windows can't decode the video in this file." |
| **Web Media Extensions** (Microsoft Store, free) | Reading `.webm` (VP8/VP9/Opus/Vorbis) | **WebM input depends on the Web Media Extensions** and on the installed Media Foundation codecs. The probe checks that WebM actually opens; if not, `.webm` files are unknown files (Zip only). |
| **MP3 / FLAC / H.264 / AAC encoder MFTs** | MP3, FLAC, MP4/M4V, M4A, video and audio Compress | The matching tiles are hidden. FLAC encoding needs Windows 10 1703 or later. |
| **Microsoft Word** | Legacy `.doc` input; higher-fidelity PDF export from DOCX | **Off by default.** MikeShift is fully local; Word is used only when you turn on **Settings -> "Use Microsoft Word for Word documents"** (command line: `--use-word` on that run; without it the CLI never starts Word). **Legacy `.doc` needs Word, turned on**: otherwise `.doc` files get no document conversions, only Zip, and the wheel says "Turn on Microsoft Word in Settings to convert .doc files" (if Word is not installed at all, the error is "Legacy .doc files need Microsoft Word to be installed."). A `.doc` that is not an OLE2/ZIP/RTF/plain-text file is refused before Word is started ("This isn't a valid Word document (.doc); it may be damaged."). Without Word (not installed, or not turned on), PDF is produced by MikeShift's own text layout (below). Word runs invisibly in the background on a private copy of the file, with alerts off, and is always quit afterwards; each conversion takes a second or two longer than the built-in converters because Word has to start. Word conversions run one at a time. **Word is not part of MikeShift and is not offline**: measured on the development PC, each Word instance started for a conversion opened HTTPS connections to Microsoft addresses (port 443) while MikeShift's own processes opened none. Leaving the setting off (the default), not having Word, or converting anything other than `.doc`/DOCX to PDF avoids it. A conversion that has not finished after **90 s** (a hung Word, a dialog nobody can see) is stopped and fails with "Word didn't respond, so the conversion was stopped."; MikeShift ends only the Word process it started itself, never one you already had open, and does the same when you cancel. |

## Where Windows hides things from MikeShift

* **Elevated (administrator) windows are invisible.** Windows (UIPI) stops a normal program from seeing the mouse and keyboard events of a higher-integrity window, and from receiving its drops. Shift-drag from an elevated Explorer window or an elevated app shows no wheel. MikeShift itself must not run as administrator for the same reason: if started elevated it shows a warning at startup. A signed `uiAccess` build is a possible future change.
* **Virtual files are refused with a hint.** Attachments dragged from Outlook, entries inside a `.zip` opened in Explorer, files on phones (MTP), and images dragged from a browser are not files on disk at drag time; their data exists only while the drop is being delivered. The wheel shows **"Save the file first"** and refuses the drop (effect NONE, nothing is converted or copied). Save the file somewhere, then drag the saved file.
* **Programs that do not use standard OLE drag and drop** (some games, some cross-platform toolkits, remote-desktop clients) never deliver the file list, so no wheel appears. If no file list arrives within 250 ms of Shift, the wheel hides again silently. Consequently **a bare disc can flash for up to 250 ms** when you press Shift during a drag that is not a file drag (a window move, a text selection): the wheel is shown before Windows says what is being dragged, because that is the only way to receive the drag at all.
* **Cloud placeholders** (OneDrive "online only" files) are classified by extension only, without downloading them. Converting one downloads it first, as any program reading it would.
* **Dragging from Explorer with Shift held before clicking** also means "range select" there; MikeShift still arms once the drag starts. After a conversion, a Shift-click that re-selects the files MikeShift just produced drops those from the next selection (within 20 s), so you don't convert your own outputs.
* **The low-level hook can be removed by Windows** if the process stalls long enough to exceed the system hook timeout. MikeShift keeps the callback minimal and re-installs the hook if it notices a drag with no events, but a very long stall (for example a debugger break) can still cost one gesture.
* **Big selections are classified by sample.** Up to 16 files every file is checked by its content (a misnamed file is noticed). For a larger selection whose extensions all agree, MikeShift confirms them on a sample of 12 files so the wheel appears at once; a misnamed file that is not in the sample then fails alone with its own `error:` message when converted, and the rest are converted. A large selection with mixed extensions is checked in full.

## The Explorer right-click entry ("Convert with MikeShift")

Design and measurements: [ARCHITECTURE.md §9](ARCHITECTURE.md). What it cannot do:

* **Only the modern menu is guaranteed on Windows 11; "Show more options" depends on the build.** Microsoft documents that the Windows 11 classic menu ("Show more options", also what a PC shows when the old menu has been forced back with a registry tweak) lists legacy handlers and that a packaged `IExplorerCommand` appears in the modern menu. On the one build tried (Windows 11 build 26300) Explorer lists the same entry, with the same submenu, in the classic menu too (Shift + right-click, or "Show more options"). **Not verified on Windows 11 21H2 to 25H2 release builds**: there the entry may be missing from the classic menu, and on a PC that forces the classic menu there would be no entry at all. The documented fix (`desktop9:FileExplorerClassicContextMenuHandler`) needs a native in-process DLL registered as a surrogate server, which the package does not carry (and which would list the entry twice on builds like 26300). Use Shift-drag or the tray's Convert files… there.
* **Windows 10 1809 and later: declared, not tested.** The same manifest registration (`desktop4:FileExplorerContextMenus`, Windows 10 1803; `desktop5:ItemType`, 1809 = the package minimum) is what makes the entry appear on Windows 10, in its single context menu. No Windows 10 PC was available, so this is Microsoft's documented behaviour, not something MikeShift has been seen doing there.
* **One level of submenu.** Explorer does not support sub-commands of sub-commands, so the menu is: the 5 most useful actions, Zip, "More options…". Everything else (the rest of the formats, Crop, Trim, Strip EXIF…) is behind "More options…", which opens the click-mode wheel **at the pointer** (where the line was clicked, kept on the screen). The modern flyout draws no separator line before "More options…".
* **The menu is built without opening files.** Lines are chosen by file extension and by what the tray app last cached about this PC, so a misnamed file gets the menu of its extension, and a DOCX with pictures is offered PDF. When the entry is clicked the tray app checks the files for real; if the action does not fit, the wheel opens with what is possible (usually Zip) instead of an error.
* **HEIC, HEIF and AVIF photos Windows cannot open get one line.** When every selected file is one of these and the tray app's cache says the decoder is missing, the submenu is **"Get the free HEIF extension"** (or "Get the HEVC video extension", "Get the free AV1 extension") and Zip, and picking it opens that extension's Microsoft Store page (the same as the wheel's tile). A mixed selection (a HEIC next to a JPG) gets the ordinary menu, and the HEIC then fails with the same advice. If the extension was installed after MikeShift started, the line stays until MikeShift is restarted (the Settings page offers the restart); picking it then opens the wheel instead.
* **A big selection is judged from Explorer's sample.** While it builds the menu Explorer hands the extension only 16 items of a larger selection (600 selected files: 16 seen, 600 delivered to the click), so a selection of mixed kinds can still be offered image conversions; the click then falls back to the wheel as above. Zip and the conversions run on the whole selection.
* **Hidden for things that are not files on disk**: virtual folders, devices, items inside a `.zip` opened in Explorer, search results of non-file items. There is no entry on a folder's empty background or on a drive.
* **First right-click after a quiet spell is slower.** The extension process starts on demand and exits after 10 idle minutes: starting it takes about half a second (the menu appears about 50 ms later than without MikeShift once it is warm). If the tray app has been exited, the first click starts it (about 1.5 s) and the action runs when it is up.
* **Right after a fresh install the submenu is conservative**: until the tray app has probed this PC's codecs once (a second or so after it starts), the menu offers only what needs no optional codec (for example TIFF instead of WebP) and never the "Get the free HEIF extension" line (it cannot know yet whether the extension is missing).
* **The Resize line follows the Settings choice** ("Resize 25%"); the tray app tells the extension process through a small file, so the menu catches up the next time it is drawn. A line drawn before the setting changed still runs the tool the setting says now.
* **A package registered or updated while Explorer is running may need Explorer restarted (or a sign-out) before the entry shows**, Microsoft's note for all packaged context-menu commands. In the tests here the entry showed up without that.
* Needs the package: unpackaged `MikeShift.exe` runs and `dotnet run` have no right-click entry. Uninstalling the package removes it.

## Conversions: what is refused and why

Messages are shown in the toast or dialog; the CLI prints them as `error: …`. A batch converts what it can and lists the files that failed.

**Images**
* Longer than 200 megapixels: "This image is too large (N megapixels). MikeShift handles up to 200 megapixels." (or "{name} is too large to convert (over 200 megapixels).")
* Decodes blank (usually a truncated HEIC/AVIF or a missing codec): "Couldn't read this image. It decoded as blank, so the file may be damaged or a codec is missing." Otherwise "Couldn't read this image. The file may be damaged." / "… or in a format Windows can't open."
* Compress, Resize and Crop refuse animated images ("Animated images can't be … without losing the animation") and multi-page files such as multi-page TIFF ("This file has N pages, and only the first would be kept, so it can't be …").
* Compress keeps the result only if it is at least 5 % smaller: "This image is already small, so compressing it wouldn't save much space." JPEG output is flattened on white; images with real transparency compress to PNG (the only output here that keeps it), so they are often "already small". HEIC output is also flattened on white, because Windows' HEIF encoder cannot store transparency.
* Crop is refused up front, before the editor opens, for animated GIF, PNG and WebP and for multi-page TIFF, so you never crop and then get an error. For HEIC photos on a PC without a HEIF encoder the **Compress** tile is hidden (it would have nothing to save the result as; see the HEIF row above).
* Crop: "The crop area is outside the image." / "The cropped picture would be too large."
* "There isn't enough memory to process this image."

**PDF**
* Password-protected: "This PDF is password-protected." Damaged: "This PDF is damaged and can't be read." / "This file isn't a valid PDF." A `.pdf` without the `%PDF` header is not treated as a PDF, and a misnamed PDF is. "This PDF has no pages." Files over 2 GB: "This PDF is too large to process."
* PDF to image: up to 2× scale and 8000 px on the long side, white background, using the Windows PDF renderer (so rendering matches what Windows draws, not Acrobat). "Page N could not be rendered."
* PDF to TXT: no extractable text: "probably a scan" (no OCR). Hebrew text stored in reverse is refused rather than written reversed.
* **Any encrypted PDF is refused** by Split, Merge, Compress, PDF to TXT and PDF to images, including one that opens without a password but carries owner-password restrictions (no printing, no copying): MikeShift does not work around restrictions the owner set.
* PDF Compress recompresses images only (skips images with masks/soft masks) and keeps the result only if smaller ("This PDF is already small — compressing it wouldn't make it any smaller.").

**Documents**
* DOCX and ODT must start with the ZIP signature `PK`: "This isn't a valid DOCX file (it may be password-protected or damaged)." Damaged packages: "This DOCX file is damaged and can't be read." / "… has no document body." RTF: "This isn't a valid RTF file." ODT: "This ODT file has no content." / "… is too large to convert."
* **Documents that contain pictures offer TXT only**, because the converters do not carry pictures across (parity with the original): "This document contains pictures, so it can only be converted to TXT."
* **PDF from documents uses MikeShift's own text layout** (PDFsharp: fixed 54 pt margins, black text, simple paragraphs, headings, lists and simple ruled tables, hard page breaks). **It will not match Word's pagination, fonts or styling** (no columns, floating objects, headers/footers or tracked changes). For DOCX with Word installed and turned on in Settings (or `--use-word`), PDF is exported by Word instead (falling back to this layout if Word fails). Very long documents are refused: "This document is too long to convert to PDF." (2,000,000 characters; 400,000 for right-to-left text).
* **Hebrew and other right-to-left text in PDF output is laid out in visual order** by a small reordering step (PDFsharp draws glyphs left to right); **there is no Arabic contextual shaping**, so Arabic letters appear in their isolated forms. Use DOCX→PDF through Word for those.
* **Non-Latin text in PDF output uses the fonts installed in Windows**: CJK in Yu Gothic, Korean in Malgun Gothic, Indic scripts in Nirmala UI, Thai and Myanmar in Leelawadee UI, symbols in Segoe UI Symbol and emoji in Segoe UI Emoji. If a font is missing on the PC, that text shows as boxes. Emoji are monochrome (no colour glyphs), and there is no complex-script shaping beyond the right-to-left reordering above, so scripts that need contextual forms or reordering of marks look plainer than in Word.
* RTF is read as a practical subset (text, paragraphs, basic character formatting); HTML is read tolerantly as text structure only and never fetches anything.

**Video and audio**
* "Windows can't open this file." / "Windows can't decode the video (or audio) in this file." (missing codec); "This file has no video." / "no audio."; "Windows Media Foundation is not available on this PC."
* Extract-audio from video offers M4A and MP3 only ("Only M4A and MP3 can be extracted from a video.").
* Compress targets 720p H.264/AAC (audio: AAC M4A) and keeps the result only if smaller: "This video is already small enough." / "This audio is already small enough."
* WAV and AIFF files are limited to 4 GB ("This audio is too long for a WAV file (over 4 GB)."); AIFF is read and written by MikeShift's own code ("This AIFF file is damaged.").
* Trim: "The trim range is empty." / "The trim range starts after the end of the file." Trim re-encodes (above).
* GIF: first 15 s (Settings: 5, 10, 15 or 30 s), 10 fps, long side at most 480 px, no dithering (above).

**Zip**
* Named pipes, sockets and device files are refused ("… is a pipe, socket or device and can't be zipped."). Folders that are cloud placeholders (OneDrive "online only" and the like) are included (zipping downloads them), but symbolic links and junctions are skipped, so a folder loop cannot happen. "Nothing to zip." / "… no longer exists."

## Conversion settings

Settings has a **Conversions** group; the command line has the same five as flags (`--quality`, `--compress`, `--resize`, `--gif-seconds`, `--out`). Without touching them everything behaves as it always did.

* **Picture quality (50 to 100, default 90)** is the quality of JPG, WebP and HEIC output: converting to those formats, Resize and Crop of such pictures, and PDF pages saved as JPG. PNG, TIFF, BMP and GIF are lossless or palette formats and ignore it. It does **not** change Compress (that has its own strength), Strip EXIF (always 95), images placed in a PDF, or video and audio.
* **Compress strength (Light, Medium, Strong; default Medium)** applies to the picture Compress tool only (longest side 4000, 3000 or 2000 px; quality 0.75, 0.6 or 0.45). PDF, video and audio Compress keep their own fixed settings. A strong setting is more likely to leave a small file as it was ("already small" is still the answer when less than 5 % would be saved).
* **Resize (25, 50 or 75 %; default 50)** is a choice of three, not a free percentage or a pixel size; the tool, its output name (`photo 25%.jpg`) and the toast say which. Each side is rounded to the nearest whole pixel, and a side never goes below 1.
* **GIF length (5, 10, 15 or 30 s; default 15)** is the longest a GIF made from a video runs; a shorter video gives a shorter GIF. GIFs stay 10 frames a second and at most 480 px wide, so 30 s can be a large file.
* **Where converted files go** is "next to the original" or one folder for every output, Merge PDF, Merge and Zip included. A folder that does not exist (a removed drive, a deleted folder; it is not recreated) or cannot be written to sends the files to **Downloads** for that job, and the toast says "In Downloads (Converted isn't available)"; Settings shows a warning next to the folder. Name collisions are resolved as always (` 2`, ` 3`), which matters when files with the same name come from different folders.
* **The command line never reads Settings.** A script gives the same result on every PC; flags are the only way to change a run. A flag outside its range (`--quality 40`, `--resize 60`, `--gif-seconds 20`, `--compress heavy`), an `--out` folder that does not exist, or `--run "Resize 25%"` together with `--resize 75` is a usage error (exit 2).
* **Not offered:** a custom percentage or pixel size for Resize, per-format quality, named presets, and output naming templates.

## Output location

Outputs are written next to the original, or into the folder chosen in Settings (see above). If that folder is not writable (read-only share, protected folder), they go to your **Downloads** folder and the toast says "in Downloads". Names never overwrite: ` 2`, ` 3`… are appended. A failed conversion leaves no output and no temporary file behind. While a job runs, its temporary output lives in a hidden folder named `.name.guid.mikeshift-tmp` next to where the result will go; it is moved into place when the job finishes. If MikeShift is killed or Windows crashes in the middle of a job, that folder can be left behind and is safe to delete.

## Packaging, memory and platform

* Windows 10 version 1809 (build 17763) or later, x64 or ARM64. The ARM64 package builds in CI but has not been run on ARM64 hardware.
* Size: the default (sideload) packages are about 45 MB per architecture (x64 44.9 MB, ARM64 43.6 MB; the combined bundle 88 MB; about 112 MB installed) because they are IL-trimmed and carry the .NET runtime and the Windows App SDK; the command-line tool runs on the same trimmed runtime instead of bringing a second copy. The Windows App SDK's on-device AI components (ONNX Runtime, DirectML) are **not** shipped (see ARCHITECTURE.md §7). History: 305 MB (bundle) -> 257 MB (no AI components) -> 158 MB (CLI shares the runtime) -> 88 MB (trimming). `mikeshift.exe` becomes available in a new terminal after install.
* **The "store" flavour (`release.ps1 -Flavor store`, about 23 MB per architecture) needs the Windows App Runtime 2.5 or later on the PC** (the framework package `Microsoft.WindowsAppRuntime.2`, x64 or ARM64 to match). The Microsoft Store installs it automatically; for a sideloaded install it has to be present first (Microsoft's `WindowsAppRuntimeInstall` installer, see the README). Without it Windows refuses to install the package and names the missing dependency. The default packages do not need it.
* Idle, the app holds roughly 17 MB working set (about 5 MB private) on the development PC; during a gesture, or while an editor is open, it needs more (about 115 MB private for the wheel in a fresh process, about 190 MB with the crop editor) and gives it back a few seconds later. The first Shift-drag after the app has been idle for more than 15 s re-creates the graphics device when the mouse button goes down; if the button is released and Shift pressed within ~100 ms of that, the wheel can take up to that long to appear instead of the usual ~30 ms.
* Dev-only switches (`MIKESHIFT_*` variables and flags such as `--scene`) are ignored by an installed MikeShift and by any Release build that is not started unpackaged with `--dev`; the list is in ARCHITECTURE.md §8.
